### What One Run Does

1. **Find the cuts.** With `--start` / `--end` it uses those times (`43:40`,
   `1:17:24` or seconds). Without them it transcribes the recording, then asks a
   language model where the sermon starts and ends.
2. **Show the plan.** File, cuts, the exact words at each cut, alternatives the
   model offered, warnings, and where the files will go.
3. **Listen first.** A 23 second clip: a few seconds before the start cut, a
   BEEP exactly at the cut, the first seconds of the sermon, then the same around
   the end cut. The screen lists the words before and after each beep and shows a
   live position line. Enter accepts; `r` replays; `s 40:55` / `e 1:17:30` move a
   cut; `s +2` / `e -0.5` nudge by any number of seconds; `q` cancels.
4. **Render in one ffmpeg pass.** Trim, fade (1s), loudness match, intro, 2.5s
   silence, sermon, 2.5s silence, outro. Progress bar with time left.
5. **Write three files** in `output/sermon/`: `DATE.wav` (master, edit in
   Audacity), `DATE.mp3` (ready to use), `DATE.json` (record for reruns). Then a
   notification, and the wav opens in Audacity.

### Commands

```
python3 sermon setup                       # once: private .venv with the extras
python3 sermon audio <file>                # auto-finds the cuts
python3 sermon audio <file> --start 43:40 --end 1:17:24
python3 sermon audio <file> --plan-only    # show the cuts, render nothing
```

Other flags: `--date YYYY-MM-DD` (default: most recent Sunday, today if Sunday),
`--format both|wav|mp3` (default both), `--fade`, `--gap` (default 2.5, 0 for
none), `--no-open`, `--no-preview`, `-y` (skip listening; refuses if an automatic
cut has a warning or low confidence), `--keep-days` (cache pruning, default 28,
0 for never), `--stream-id`, `--output-dir`, `--config`.

## How The Cut Finding Works

1. Transcribe with word-level timestamps (faster-whisper `base.en` locally, or a
   hosted Whisper-class API). The transcript is cached by file in
   `cache/transcripts/`.
2. Build a text view for the model: one line per stretch of speech with
   `[H:MM:SS]`, plus markers like `(no speech for 4:01: likely music or singing)`
   where a stretch is quiet.
3. Send Paul's guidance plus that text. The model must return start and end
   times, the exact words at each boundary, confidence, a reason, and optional
   alternatives.
4. Do not trust the model's times. Find its quoted words in the word stream near
   its claimed time and place the cut on the real word. Pads: 1.0s before the
   start word, 2.0s after the end word, but never inside the neighbouring word
   (if the neighbour is closer, cut halfway into the gap).
5. If a quote contains a pause over 3 seconds, it spans two speakers (for
   example "Thank you." then the reading). The start moves to after the pause,
   the end to before it, with a warning.
6. Warn if a cut moved more than 30s from the model's own time, if quotes could
   not be found, or if the result is under 10 minutes.

### Paul's Rules (see `config/trim_guidance.md`, which is the source of truth)

- **Start:** when the scripture reader begins ("Today's scripture reading comes
  from..."), after the announcements end. Not the preacher's first words.
- **End:** the "amen" of the closing prayer that comes directly after the
  sermon, before the final worship song. The preacher often comes back after the
  song with a benediction or final words. Never include that, ever.
- Communion weeks: the end cue is the "amen" of the prayer, which comes right
  after the sermon.
- A sermon is usually 40 to 50 minutes.

## Decisions And The Reasons

| Decision | Why |
| --- | --- |
| Run natively with Python, keep Docker optional | Docker was for Windows and Mac parity, but it rebuilt the image on every run. Windows has no ffmpeg or make by default. The CLI uses system ffmpeg if present, else the `static-ffmpeg` package |
| `sermon setup` makes a private `.venv` | Homebrew Python refuses system-wide `pip install` (PEP 668), which broke Paul's first run |
| One ffmpeg pass, no intermediate files | The old trim, fade, normalize, concat chain left stale files that broke or skewed later runs |
| Always write wav + mp3 + json | wav to edit, mp3 to use as-is, json to rerun. Never overwrite: if any of the three exists the next run becomes `DATE-2` |
| Shared top-level `trim` in config | Audio and video were typed twice and drifted |
| 2.5s digital silence after intro and before outro | Paul's request. It sits on top of the sermon's own short lead-in and tail, so the quiet before the first word is slightly longer than 2.5s |
| Listen-before-render with a beep | Paul found a bare clip confusing and could not tell where the cut was |
| `-y` refuses unverified automatic cuts | Unattended runs must not ship a wrong cut |
| Cache pruned after 28 days, only `audio`, `video`, `transcripts`, `previews` | Paul asked for it. `output/` and `cache/s3` (intro, outro) are never touched |
| Intro and outro downloads use the standard library, via a temp file | A half-finished download could previously look cached |
| Word-level snapping, not segment edges | A Whisper segment once ran through four minutes of singing and pulled the end cut to 1:21:34 instead of 1:17:29 |

## Lessons And Bugs Already Hit (do not repeat)

- The fade step wrote AAC into a `.wav` or `.mp3` container: unreadable files.
  Pick the codec by container.
- Reusing `*_trimmed` files silently reused a previous week's trim. Re-trim every
  run.
- faster-whisper returns NumPy numbers. A comparison made a NumPy bool and
  `json.dump` crashed after a successful render. Saved transcripts hold plain
  floats, so tests that reuse them never caught it. Always test with fresh data.
- faster-whisper's own decoder (PyAV) crashed on a version mismatch. Decode with
  our own ffmpeg and pass samples.
- Silence detection cannot find cuts here: the room tone never drops below
  -35 dB. Do not try snapping to silence.
- The model sometimes begins its start quote with the previous speaker's "Thank
  you." Fixed by the pause rule and a prompt line.
- A preview screen that lists words the clip never plays is worse than none.
  List only what is audible; say "quiet" otherwise.
- The beep from ffmpeg's `sine` source is about -30 dB by default. It was raised
  to about -9 dB (`volume=3`).
- ffmpeg cannot map one filter output to two files. Split with `asplit` first.
- Whisper stores text over singing. Show quiet stretches to the model as gaps.
- Model answers vary between runs. Keep alternatives visible and keep the human
  listening step.

## Future Idea: Transcripts On The Sermon Pages

### What Is Possible

- A word-by-word transcript on each sermon page.
- A read-along that highlights the current word as the sermon plays.
- A `.vtt` captions file per sermon, also uploadable to YouTube.
- Corrections by staff, with the machine's original kept.

### Accuracy (Measured Lightly)

- `base.en` (current) makes visible mistakes: "Exerbs of Exodus", "Refodym" for
  "Rephidim", "Interfection and love for you are Savior and Lord". Names and
  Bible places are the weak spot.
- `small.en` differs from `base.en` on about 2.4% of words in a 6 minute slice,
  mostly improvements ("treasuret possession" to "treasured possession"). That is
  disagreement between two models, not an error rate; no ground truth was
  measured.
- Word times were usually close but one was about a second off, next to music.
  Fine for jumping around, noticeable for a per-word highlight. Forced alignment
  after edits would fix drift.
- Improve with: a bigger or hosted model; transcribing only the sermon, not the
  service; a vocabulary list of names, Bible books and places (faster-whisper
  supports a prompt or hotwords); a shared find-and-replace list for repeated
  errors; saving per-passage confidence so reviewers start with the shaky parts.

### Speed And Cost For All 700

was `base.en` to `small.en`; `medium.en` looks like a smaller gain for roughly 3x
the time. Decide with the pilot. On Apple Silicon, `whisper.cpp` or `mlx-whisper`
(which use the Mac's GPU) are likely several times faster than faster-whisper's
CPU mode, which would make the larger models practical overnight; not tried.

Some newer hosted models do not return word-level timing; Whisper-based ones do.

### Proofreading Reality

Reading along with 583 hours is not realistic. Plan: publish the machine
transcript labelled auto-generated, add a "report a correction" link, flag low
confidence passages, hand-edit newest and most-viewed sermons first, and keep a
shared fix list.

### Editing Model

Three layers: raw machine transcript (never changed), edited transcript (what
people fix), published (the edited one). Fixing a word keeps its timing. Added or
removed words get interpolated timings. A re-run must never overwrite edits.
Optionally re-align after larger edits.

### Storage Recommendation

Not one blob per sermon. One row per paragraph (about 150 to 250 words):

```
transcript_chunk   sermon_id, transcript_version, idx, start_ms, end_ms,
                   text, words jsonb [[start_ms,end_ms,"word"],...],
                   tsv tsvector, embedding vector(...), edited_by, edited_at
transcript_revision   undo history
sermon_topic          themes, scripture references, key stories, confidence
```

- Size: about 8,500 words per 50 minute sermon; about 184 KB as a compact
  `[start,end,text]` list (about 61 KB gzipped); about 130 MB for all 700.
- A single JSONB blob per sermon is the quickest start (about a day) but needs
  reshaping once search and editing arrive.
- Read-along: look up the current word by playback time. The YouTube player has
  no time event, so poll its current time several times a second; for an
  `<audio>` element use animation-frame polling.

## Future Idea: Search And Sermon Lookup Through An LLM

Goal: when anyone asks an LLM about a Bible topic or passage, surface Metro
sermons that preached on it or mentioned it, with a link to the exact moment.
Paul already has a `reformed-research` skill.

### Pieces

1. **Scripture index.** Detect references in speech ("Romans eight", "chapter 8
   verse 1") and normalize to book, chapter and verse range. Later, catch quotes
   with no reference by matching transcript paragraphs to a public-domain Bible
   (KJV or WEB) for matching only; embeddings handle the wording differences
   from modern translations. The sermon's `passage` field separates "preached
   on" from "mentioned".
2. **Topic search.** Postgres full-text (phrases, OR, exclusions, highlighting),
   `pg_trgm` for spelling slips on names, and `pgvector` embeddings per
   paragraph, ranked together. Tag each sermon once with a model for themes,
   scripture and illustrations. About 28,000 paragraphs is small for Postgres; no
   separate search engine is needed.
3. **MCP server**, read-only, with a few tools: search by topic, find sermons by
   passage, fetch an excerpt around a timestamp. Each result returns speaker,
   date, series, a short excerpt and a link that opens at that moment.
4. **Skill update.** Tell `reformed-research` to call those tools after answering
   a Bible or theology question and add "Metro sermons on this."

Estimated size once transcript search exists: days, not weeks (rough).
Embedding and tagging all 700 should cost tens of dollars at most (not priced).

### Limits And Cautions

- An MCP server only helps people who connect it (Paul, staff, via a remote
  server with a login). For the public, publish crawlable pages such as "Sermons
  on Romans 8" and "Sermons on forgiveness".
- Return quoted excerpts with links, not paraphrases of what a preacher believes,
  so a mis-transcribed word cannot put wrong words in someone's mouth. A mention
  is not an endorsement.
- Check comfort with indexing guest speakers publicly.
- Keep members-only content (the site has courses) out of the index.
- Build a test set of about 30 queries and check that the right sermons come
  back before relying on topic matching.

## Intro And Outro Marking (Later)

Plan: transcribe everything identically, then mark (not delete) the standard
intro and outro so search and any sentiment or topic analysis can skip them.
Earlier years have no intro at all, so marking has to be optional.

The standard clips are in `cache/s3/` (`audio_intro.wav`, `audio_outro.wav`).
Transcribed with `small.en`, they say:

- **Intro (about 18.5s):** "Welcome to the Metro Church podcast. We are a warm
  and vibrant Gospel Center church with campuses in the Philadelphia region,
  passionate about the Gospel, community, and discipleship. If you'd like to
  learn more about joining our community, or would like to give to our ministry,
  please visit us at MetroPhilly.org."
- **Outro (about 15.7s):** "Thanks for listening to the Metro Church podcast. If
  you are encouraged by today's teaching and are looking for a gospel community,
  we invite you to join us. To learn more, visit MetroPhilly.org. To give, visit
  MetroPhilly.org slash give."

(The transcriber wrote "Gospel Center"; the real wording is probably
"gospel-centered". Match fuzzily, not exactly.)

How: fuzzy-match the start of each transcript against the intro text and the end
against the outro text. If it matches, record `intro_end_ms` and
`outro_start_ms` on the transcript row (or a `kind` of `intro`, `body`, `outro`
on each paragraph) and exclude those from search and analysis. No match means no
intro, and nothing is marked. Wording may differ between years, so keep the match
threshold loose and allow a list of known intro texts.

## Video Alignment Ideas

The problem: the audio and the video for one sermon are often different lengths
or edited differently, so transcript times from the audio will not fit the video.
YouTube already generates its own captions for the video, which lowers the
pressure.

1. **Do nothing for the video (recommended first).** The transcript sits beside
   the audio player and the highlight follows the audio. The video keeps
   YouTube's own captions. On a page that only shows the video, show the
   transcript without a highlight, with a button that starts the audio at that
   paragraph. No risk, no extra work.
2. **Match words to YouTube's captions (best later option).** Get the video's
   caption text with its timestamps (YouTube's official API works for a channel
   Metro owns, with the owner's login; a manual caption export also works;
   `yt-dlp` may hit the bot checks already noted as flaky). Compare our word
   list with the caption word list as two sequences. Each long run of matching
   words gives an anchor pair (audio time, video time). Store the anchors per
   sermon and map times between them by straight lines. This copes with
   different intros and with cut sections, needs no audio download, and never
   guesses a single global offset. Sanity checks: the mapping must only move
   forward, and the leftover error at each anchor must be small. Quality is
   limited by the caption accuracy.
3. **Match the sound.** Download the video's audio and compare it with the S3
   audio using audio fingerprints (Chromaprint) or cross-correlation to find the
   offsets. Very robust, but it means downloading 700 videos, and the YouTube
   download was already flaky.
4. **One offset only.** If the only difference is the intro length, estimate a
   single offset from the first matched anchor and flag any sermon whose
   leftover error is large. Cheap, wrong for cut sections.
5. **Avoid transcribing the video as well.** Doing both would double the hours.
   If the video needs its own captions, upload an aligned `.vtt` instead.

Store the result as an optional list of `[audio_ms, video_ms]` anchors per
sermon, empty by default, so the feature can be added later without changing
anything else.
